# EpubFabric 規則蓄積と自律実行の設計

> 本書は設計案である。実装は着手していない。実験の位置付けは[リフロー解析バックエンド実験計画](リフロー解析バックエンド実験計画.md)、製品全体の方針は[基本設計](基本設計.md)を正とする。

## 1. 目的

リフロー型変換の判断精度を、アプリ内部の自己学習機構ではなく、開発時のエージェント（Claude Code、Codex）を教師とする規則抽出によって高める。

抽出した規則は配布物へ同梱し、利用者の環境ではエージェントなしで適用する。エージェントは開発者の手元だけで動作させ、利用者へは要求しない。

## 2. 前提と制約

本設計は次を満たすこととする。

1. 利用者環境から外部の生成AIサービスへ文書内容を送信しない（基本設計 3.3）。
2. 規則が存在しない場合、および規則の適用に失敗した場合でも、0.4.0相当の結果を生成できる（基本設計 3.4）。
3. 利用者環境にPython、APIキー、エージェントを要求しない。
4. 規則の追加は1回につき1種類とし、基準結果と比較できる状態を保つ（実験計画 4節）。
5. 手動修正した項目は規則によって上書きしない（基本設計 9.9）。
6. エージェントへ渡す対象は、開発者が保有する検証用PDFに由来する観測データに限定する。ページ画像そのものは既定では渡さず、必要な場合に開発者が個別に判断する。

## 3. 全体構成

開発時と実行時で経路を分ける。実行時の経路にエージェントは現れない。

```text
[開発時ループ（開発者の手元のみ）]

  検証用PDF
      │
      ▼
  変換（現行パイプライン）
      │
      ├─ EPUB
      └─ 観測データ observations.json
              │
              ▼
        エージェント（Claude Code / Codex）
              │
              ▼
        規則候補 proposals.json
              │
              ▼
        検証・人による採用判断
              │
              ▼
        規則ストア rules/*.json（Git管理）
              │
              ▼
        配布物へ同梱

[実行時（利用者環境）]

  PDF ─→ 変換（規則ストアを適用）─→ EPUB
```

エージェントは規則ストアへ直接書き込まない。提案を`proposals.json`へ出力し、採用は通常のコミットとして人がレビューする。これにより、蓄積内容がGit履歴に残り、規則単位で巻き戻せる。

## 4. 規則の種類と自律化の可否

蓄積対象を一括で扱わず、自律実行へ移行できる種類と、移行しない種類を分ける。

| 種類 | 内容 | 実行時の適用先 | 自律化 |
|---|---|---|---|
| 訂正規則 | 誤認識文字列と正解の対応 | OCR文字列の後処理 | する |
| 余白規則 | 柱・ノンブル・広告などの座標帯と扱い | `RepeatedMarginClassifier` | する |
| しきい値規則 | 見出し判定の文字高比、段組み判定の係数など | `HeuristicLayoutAnalyzer`、`ColumnDetector` | する |
| 分類事例 | ブロック種別の誤判定と正解の対応 | （適用しない） | しない |

訂正規則、余白規則、しきい値規則は決定論的な処理に落ちるため、規則が確定した時点でエージェントが不要になる。

分類事例は文脈依存であり、事例を増やしても未知の紙面で頭打ちになる。本設計では蓄積のみ行い、実行時には適用しない。将来の追加学習（LoRA等）に備えた教師データとして形式だけ定める。

## 5. 観測データ

### 5.1 目的

エージェントへ渡す入力であり、同時に規則の根拠となる。既存の`metrics.json`（`EvaluationSummary`）は集計値のみであるため、個々の判断を特定できる観測項目を別ファイルとして出力する。

### 5.2 出力位置

`evaluate`コマンドのレポートディレクトリへ`observations.json`として出力する。既定では出力せず、明示的な指定時のみ生成する。

### 5.3 観測項目

| 種別 | 抽出条件 | 用途 |
|---|---|---|
| `lowConfidenceOcr` | `OcrConfidence`がしきい値未満 | 訂正規則 |
| `manualTextCorrection` | `IsManuallyEdited`かつ`CorrectedText`あり | 訂正規則（確定扱い） |
| `manualTypeChange` | `IsManuallyEdited`かつ種別変更 | 分類事例、しきい値規則 |
| `repeatedRegion` | 同一座標帯に複数ページで出現するブロック | 余白規則 |
| `droppedText` | `TextCharsDropped`に計上された文字 | 欠落の調査 |
| `baselineDiff` | 基準結果との差分 | 退行検出 |

### 5.4 形式

```json
{
  "generatedAt": "2026-09-13T10:00:00+09:00",
  "commit": "c67eb6a",
  "source": { "file": "地理_202601.pdf", "pageCount": 30, "dpi": 300 },
  "options": { "layout": "reflow", "ndlocr": "native" },
  "observations": [
    {
      "kind": "manualTextCorrection",
      "page": 15,
      "blockId": "b-015-007",
      "bounds": { "x": 0.11, "y": 0.22, "w": 0.32, "h": 0.05 },
      "writingMode": "Vertical",
      "textSource": "NdlOcr",
      "before": "解脱がある",
      "after": "解説がある"
    }
  ]
}
```

## 6. 規則ストア

### 6.1 置き場所

リポジトリ内の`rules/`へ置き、Gitで管理する。配布物へは読み取り専用として同梱する。利用者環境で書き換えない。

### 6.2 共通項目

| 項目 | 内容 |
|---|---|
| `id` | 規則の識別子 |
| `kind` | `textCorrection` / `marginExclusion` / `threshold` |
| `scope` | `global`、または`publication:<誌名>` |
| `condition` | 適用条件 |
| `action` | 適用内容 |
| `origin` | `manual`（手動修正由来）／`agent`（エージェント提案） |
| `occurrences` | 独立に確認できた出現回数 |
| `evidence` | 出典（PDF名、ページ、ブロックID） |
| `status` | `candidate` / `confirmed` / `rejected` |

`rejected`の規則も削除せず残す。同じ提案が繰り返し上がることを防ぐ。

### 6.3 例

```json
{
  "id": "corr-0007",
  "kind": "textCorrection",
  "scope": "global",
  "condition": { "pattern": "入カ" },
  "action": { "replacement": "入力" },
  "origin": "manual",
  "occurrences": 12,
  "evidence": [ { "file": "科学_202601.pdf", "page": 14, "blockId": "b-014-003" } ],
  "status": "confirmed"
}
```

```json
{
  "id": "margin-0003",
  "kind": "marginExclusion",
  "scope": "publication:地理",
  "condition": { "writingMode": "Vertical", "band": { "x": 0.02, "y": 0.90, "w": 0.96, "h": 0.08 } },
  "action": { "type": "PageNumber", "exclude": true },
  "origin": "agent",
  "occurrences": 24,
  "status": "candidate"
}
```

### 6.4 適用範囲

`scope`が`global`の規則は全文書へ適用する。書誌固有の語や紙面設計は`publication:`へ限定し、他誌への誤爆を防ぐ。

書誌の対応付けは、初期段階では変換時の明示指定とする。自動判定は行わない。

## 7. 実行時の適用順序

```text
1. 文字取得（PDF文字層 / RapidOCR / NDLOCR-Lite）
2. 訂正規則の適用（決定論的置換）
3. レイアウト解析（しきい値規則を初期値として使用）
4. 余白規則による柱・ノンブル等の分類と除外
5. 既存の分類（ヒューリスティクス → Ollama）
6. 検証
```

訂正規則は`OcrTextCorrector`より前に適用する。規則で直る誤りはLLMへ送らず、処理時間と応答のばらつきを減らす。

規則由来の変更にも、`OcrTextCorrector`の既存ガード（変更文字数の許容割合、英数字連続列の保護）と同じ検証を適用する。規則は一度人が承認したものであって、無条件に正しいものではない。

優先順位は次のとおりとする。上位が常に勝つ。

```text
手動修正 > confirmed規則 > candidate規則 > ヒューリスティクス > Ollama
```

## 8. 昇格の条件

`candidate`から`confirmed`への昇格条件を次のとおりとする。

1. `origin`が`manual`の場合は、1件で`confirmed`とする。
2. `origin`が`agent`の場合は、独立した3ページ以上で同じ規則が再現していること。
3. 昇格前後で評価指標が悪化しないこと（9節）。
4. 既存の`confirmed`規則と矛盾しないこと。

1回きりのエージェント判断を規則にしない。頻度による裏付けを必須とする。

## 9. 卒業判定

「エージェントなしで自律実行してよい」の判定は、規則の種類ごとに個別に行う。全種類を同時に卒業させない。

判定には既存の`EvaluationSummary`を用いる。

| 指標 | 条件 |
|---|---|
| `TextCoverage` | 規則なしの結果より低下しない |
| `TextCharsDropped` | 増加しない |
| `LowConfidenceIncludedCount` | 減少する（訂正規則の場合） |
| `HeadingCount` | 基準に対する過剰・過少が増えない |
| 読み順の重大誤り | 基準より増えない |

判定対象は検証用3冊の先頭30ページとする。1冊だけで改善し他の2冊で悪化する規則は、`scope`を`publication:`へ限定する。

## 10. 段階計画

実験計画の段階5が完了した後に着手する。並行して進めない。

| 段階 | 内容 | 完了条件 |
|---|---|---|
| A | 観測データの出力 | `observations.json`を3冊で生成でき、エージェントが読める |
| B | 規則ストアと訂正規則 | 訂正規則が実行時に適用され、卒業条件を満たす |
| C | 余白規則・しきい値規則 | 書誌単位で適用され、他誌を悪化させない |
| D | 分類事例の蓄積 | 形式を定めて蓄積する。実行時には適用しない |

段階Aだけがアプリ側の新規実装であり、段階Bまでは既存の`EpubFabric.Evaluation`と`OcrTextCorrector`の周辺にとどまる。

## 11. 対象外

次は本設計に含めない。

- 利用者環境でのエージェント実行
- 実行時における外部APIの呼び出し
- 追加学習（LoRA等）の実施。教師データの形式のみ定める
- エージェントによる規則ストアへの自動書き込みと自動コミット
- 書誌の自動判定

## 12. 想定する問題

| 問題 | 対処 |
|---|---|
| 誤った判断が規則として固定される | 昇格条件（8節）、`rejected`の保持、手動修正の優先 |
| 検証用3冊への過剰適合 | `scope`の限定、卒業判定を3冊横断で行う |
| 規則の誤爆 | 実行時の検証（7節）、規則単位の無効化 |
| 規則が増えて追跡できなくなる | Git管理、`evidence`の必須化、適用ログの出力 |
| 著作権のある紙面を外部へ渡す | 観測データに限定し、ページ画像は既定で渡さない（2節6） |
